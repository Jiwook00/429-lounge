# 인디언 포커 서버: 열린 테이블, 클라이언트 tick으로 도는 11초 타이머와 컴퓨터

## 배경과 문제

소수결([ADR-0022](0022-retire-minority.md)) 자리에 인디언 포커가 들어온다. 판마다 카드 한 장, 내 카드만 나는 못 보고, 앤티 10칩 뒤 한 바퀴 순차 베팅으로 높은 숫자가 이긴다. 회원이 몇 명뿐이라 컴퓨터가 빈 자리를 채우고, 사람 차례엔 11초 타이머가 있다. 서버에는 상주 프로세스가 없어(ADR-0003) 타이머와 컴퓨터 행동을 누가 언제 진행할지, 내 카드를 내 클라이언트에 안 보내는 방법, 올인·이탈 때 칩을 어떻게 나눌지를 정해야 했다. 이번 결정은 서버와 클라이언트 API까지이고 화면은 다음 PR이다.

## 고려 요소

- 결과와 칩은 서버 `security definer` RPC에서만 (ADR-0003), 상주 프로세스·크론 없이
- 내 카드는 판이 끝날 때까지 내 앱에 오지 않아야 한다(폴드해도). 읽기 전용 테이블과 Realtime에도 없어야 한다
- 컴퓨터는 칩이 무한이지만 사람과 같은 규칙으로 판돈에 넣고 딴다. 그 결과는 실제 사람 칩 증감이다
- 앱을 닫고 사라진 사람의 앤티가 계속 빠지면 안 된다
- 사람이 다 나가면 테이블이 닫혀야 한다

## 고려한 선택지

1. **블랙잭처럼 tick이 마감을 정산**: 앉은 클라이언트가 `ip_tick`을 부르면 마감이 지난 일을 순서대로 처리
2. Edge Function + 크론으로 1초마다 모든 테이블 진행
3. 컴퓨터 행동은 사람 행동 직후 서버가 그 자리에서 몰아서 처리, 사람만 타이머

## 결정

선택: "1". 블랙잭(ADR-0014)·룰렛과 같은 방식이라 새 인프라가 없고, 마감을 직전 마감에서 이어 계산하면 아무도 tick을 안 부른 사이의 일도 같은 결과로 따라잡힌다. "3"은 컴퓨터가 1~5초 고민하는 연출을 서버 시각으로 맞출 수 없다.

- 테이블: `ip_tables`(자리 2~4 = 만든 사람 1 + 컴퓨터 1~3, 자리별 컴퓨터 이름), `ip_members`(앉은 사람과 자리, `seen_at`), `ip_hands`(판), `ip_hand_seats`(자리별 낸 칩·행동·지급 = 판 결과 기록, 컴퓨터는 `player_id` null). 한 사람은 한 번에 한 테이블
- 로비: `ip_lobby`는 열린 테이블과 사람 수만 준다(컴퓨터 숨김, 2/4는 사람만). 아무도 tick을 안 부르는 테이블도 로비가 따라잡아 닫는다. 자동 배정·관전 없음, 자리 없으면 `ip_create`
- 입장: 들어오면 빈 자리 번호를 받고, 그 자리 컴퓨터는 다음 판부터 빠진다. 앤티(10)보다 적으면 거절
- 진행: 판 시작 때 앤티 10칩씩, 카드 1~10 한 벌을 섞어 한 장씩. 첫 행동 자리는 `(판 번호 − 1) % 자리 수 + 1`로 한 칸씩 돈다. 딜 연출 2초 뒤 첫 차례
- 행동: 체크는 아무도 안 걸었을 때만, 첫 베팅 최소 10, 레이즈는 `min_raise`(직전에 올린 폭) 이상, 횟수 제한 없음. 금액은 "지금 베팅 위로 올리는 칩". 잔액이 모자라면 가진 칩 전부 = 올인(최소 폭 미만도 허용, 그땐 최소 폭은 그대로). 올리면 다른 자리는 다시 행동한다. 행동할 자리가 없거나 하나뿐인데 이미 맞췄으면 공개
- 정산(사이드팟): 접지 않은 사람들이 낸 금액 단계마다 팟을 나누고, 그 단계까지 낸 사람 중 높은 카드가 가져간다. 올인한 사람은 각 상대에게서 자기가 낸 만큼만 딴다. 접은 칩은 판돈에 남는다. 이탈로 접은 사람이 남은 누구보다 많이 냈으면(정상 진행에선 안 생김) 그 넘는 칩은 가장 높은 단계 팟에 들어간다. 동점이면 나누고 남는 칩은 첫 행동 자리부터
- 타이머: 사람은 11초, 넘기면 tick이 자동 폴드(`timeout`). 11초 안에 다시 tick·행동하면 그대로 이어서 한다. 일어나기(`ip_leave`)는 그 자리에서 폴드(`leave`), 내 차례였으면 바로 다음 차례
- 잠수: tick·행동이 `seen_at`을 갱신한다. 판을 시작할 때 30초 넘게 안 보인 사람은 자리에서 뺀다(`away`). 따라잡기를 먼저 하고 `seen_at`을 나중에 갱신해서, 오래 비웠다 돌아온 사람은 밀린 판 시작 때 이미 빠져 있다. 사라진 사람이 잃는 칩은 앤티 두 번까지
- 닫힘: 판을 시작할 때 사람이 없으면 닫는다. 판 도중 접지 않은 사람이 없으면(컴퓨터끼리 남음) 바로 공개·정산해서 사람이 다 나가면 판이 끝나는 대로 닫힌다
- 컴퓨터: `ip_decide`가 자기 카드는 모른 채 상대 카드만 보고 승률(남은 카드 중 접지 않은 상대 최고 카드를 이기는 비율)을 계산해, 강하면 베팅·레이즈, 판돈 대비 콜 값이 맞으면 콜, 가끔 허세·폴드. 베팅은 판돈의 절반~전부를 10칩 단위로 200칩까지, 판당 세 번째 레이즈부터는 안 올린다. 차례가 오면 1~5초 뒤가 마감이고 그 마감의 tick에서 행동한다. 난이도 선택 없음, 하루 한도 없음
- 카드 가림: 카드는 `ip_cards`에만 있다. RLS 정책이 없고 권한도 회수해 클라이언트와 Realtime에 안 나간다. `ip_state`는 부른 사람이 이번 판에 앉은 자리의 카드를 늘 빼고, 테이블에 앉지 않은 사람에겐 전부 뺀다. 끝난 판은 전부 공개
- 결과 5초 뒤 다음 판. 이번 주 큰손(`game_results`)엔 `indian_poker`로 한 판 = 지급 − 낸 칩(앤티 포함), 컴퓨터 자리는 뺀다
- 클라이언트는 `ip_*` RPC가 주는 jsonb 하나만 그린다. Realtime(`ip_tables`·`ip_members`·`ip_hands`·`ip_hand_seats`)은 "바뀌었다" 신호로만. 앉아 있는 동안은 1~2초마다, 그리고 마감 시각에 `ip_tick`
- 기존 RPC를 바꾸지 않아 `client_policy.min_version`은 그대로

### 결과

- 좋은 점: 새 인프라 없이 블랙잭과 같은 진행 방식. 아무도 없던 시간도 다음 tick에서 같은 규칙으로 따라잡는다
- 좋은 점: 카드가 읽기 가능한 곳에 없어서 앱을 고쳐도 내 카드를 볼 수 없다
- 좋은 점: 컴퓨터끼리 시뮬레이션(800판)에서 판마다 지급 합 = 판돈, 사람 칩 변화 = −컴퓨터 순수익이 맞았다 (`supabase/tests/indian_poker.sql`)
- 나쁜 점: 아무도 tick을 안 부르면 컴퓨터 1~5초, 사람 11초가 늦어질 수 있다. 앉은 앱이 tick을 계속 불러야 한다
- 나쁜 점: 컴퓨터 칩이 무한이라 사람이 크게 올인하면 컴퓨터 상대 승리로 칩이 새로 생긴다. 시뮬레이션에서 컴퓨터 순수익은 판당 약 −1.3칩(사람이 조금 땀). 한도 없이 두고 실제 데이터로 판단한다
- 나쁜 점: 앱이 죽으면 다음 판 앤티까지 빠질 수 있다(30초 유예)

## 선택지별 장단점

### 2. Edge Function + 크론

- 좋음: 아무도 안 봐도 시간이 정확하다
- 나쁨: 새 인프라와 비용, 크론 최소 간격(1분)으로는 1~5초를 못 맞춘다

### 3. 컴퓨터는 즉시, 사람만 타이머

- 좋음: tick이 할 일이 시간 초과뿐이라 단순
- 나쁨: 컴퓨터 고민 연출을 앱이 지어내야 하고, 앱마다 다르게 보일 수 있다
