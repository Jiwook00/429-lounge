# 게임 결과·칩은 서버 RPC에서만, 라운드는 지연 정산

## 배경과 문제

칩이 걸린 게임이라 결과를 클라이언트가 정하면 바로 조작된다. 동시에 라운드를 돌리는 서버 프로세스나 크론은 두고 싶지 않다.

## 고려 요소

- 결과(구슬 개수 등)는 정산 전까지 클라이언트에 노출되지 않을 것
- 여러 클라이언트가 동시에 요청해도 한 번만 정산될 것
- 아무도 없는 방은 비용이 0일 것

## 고려한 선택지

1. 클라이언트가 결과를 정하고 서버는 기록만
2. 크론(pg_cron) 또는 Edge Function이 주기적으로 라운드 진행
3. RPC 호출 시점에 정산하는 지연 정산 (lazy tick)

## 결정

선택: "지연 정산". 규칙은 이렇다.

- 테이블은 RLS로 **읽기만** 연다. 모든 쓰기는 `security definer` 함수(`oddeven_tick`, `oddeven_bet`, `claim_*` 등)로만 한다
- `oddeven_tick(room)`: 방의 현재 라운드를 돌려준다. 마감이 지났으면 그 자리에서 결과를 뽑아 정산하고, 결과 연출 시간(5초) 뒤에 열리는 다음 라운드를 만든다
- 같은 방의 tick/bet은 `pg_advisory_xact_lock`으로 직렬화해서 동시에 불러도 한 번만 정산된다
- 테이블에 앉은 클라이언트가 마감 시각에 tick을 부른다. 그 사이 변경은 Realtime으로 받는다

### 결과

- 좋은 점: 서버 프로세스 없음. 빈 방은 아무 일도 안 함. 결과는 정산 순간에만 생성됨
- 좋은 점: 새 게임도 "읽기 전용 테이블 + 쓰기 RPC + tick" 패턴을 그대로 쓰면 됨
- 나쁜 점: 아무도 tick을 안 부르면 정산이 늦어진다 (베팅한 사람이 떠나도, 다음에 누군가 들어오면 정산됨)
- 나쁜 점: 클라이언트 시계가 서버와 어긋나면 tick 타이밍이 조금 밀린다 (0.3~5초 주기로 다시 맞춤)
- 나쁜 점: `random()`은 암호학적 난수가 아님. 소규모 회원제 라운지라 허용, 필요하면 `gen_random_bytes`로 교체

## 선택지별 장단점

### 클라이언트 결정

- 좋음: 가장 단순, 지연 없음
- 나쁨: 조작 가능. 칩 게임에선 선택지가 아님

### 크론 / Edge Function

- 좋음: 정확한 타이밍
- 나쁨: 빈 방도 계속 돌아감. pg_cron은 초 단위 라운드에 맞지 않고, Edge Function은 로컬 스택에서 꺼둔 상태
